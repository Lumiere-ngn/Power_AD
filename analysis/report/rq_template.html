Both questions were tested on the hourly Prometheus telemetry alone (March–October 2026). The answers below are what this data supports; the last section lists what the Linux logs would add.

RQ1

Normal-behaviour modelling

    What each kind of context buys

    Test error (Aug–Oct) as feature groups are added to one LightGBM model shared by the whole fleet. Each step adds a group to the previous one; the last step lets the model learn a per-device offset. Lower is better.

    Models compared

    Temporal hold-out: fitted on data before 1 August, scored on 1 August – 6 October for devices seen in training. Within-device R² compares the error to each device's own test-period mean, so it scores how well a model follows a device's variation rather than how well it tells devices apart. Persistence uses the previous hour's value of the target and is shown only as a reference point: a normal-behaviour model must not see the target, or it would follow an anomaly instead of flagging it.

    Which context matters for which target

    Increase in test MAE when one group is removed from the full model (time, hardware, environment and workload). Large bars mark the context that target cannot do without.

    Expected behaviour, hour by hour

    Ten test days on one device: the measured value, the model's median and its 90 % band (quantile models with device identity). This band is the normal envelope an anomaly detector compares against.

    By fault and severity

    Share of injected episodes detected, per fault. F6 is a cooling fault with no change in power: a control case outside the energy faults, and not counted in the headline numbers.

    Finding the faulty measurement

    After an alarm, the node with the largest mean score over the episode is reported as the cause. Accuracy is the share of energy-fault episodes where that node is the injected root.
